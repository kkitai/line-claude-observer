# Project Conventions

## File Deletion Policy
- Even if permission bypass is in effect, always obtain approval before deleting any files.

## README Generation Policy
- Place README.md in the project root.
- README.md must include the following sections and be kept up to date at all times:
  - Application overview
  - How to run the application
  - How to run Unit Tests
  - How to run E2E Tests

## Application Code Generation Policy
- When creating application code, follow the standard directory structure for the chosen programming language.

## Test Code Generation Policy
- When generating application code, implement Unit Tests at the same time.
- When generating application code, implement E2E Tests at the same time.
- Test code coverage must be 70% or higher.
- Test file names must follow the de facto naming conventions of the respective programming language.
- If there is no CI Pipeline for the created or modified test code, implement the CI Pipeline code at the same time. (GitHub Actions is assumed.)
- If CI fails, continue root cause analysis and fixes until resolved.

## Test Execution Policy
- Once test code implementation is complete for a meaningful unit of work, ask the user to run the tests and do not proceed to the next implementation until successful test completion is confirmed.

## Technology Conventions
- Go is the designated programming language.
- When using an RDBMS, use PostgreSQL.
- All DDL changes to the RDBMS must use goose, with migration files placed under app/db/migrations/.
- Use htmx for frontend development.
- Use Tailwind CSS (via CDN) as the CSS framework.
- Other technology choices are at your discretion.

## Frontend Implementation Policy (Integration with Claude Design)

Screen implementation is based on prototypes generated by Claude Design. Follow the rules below.

### Prototype Handoff Rules
- Before starting HTML template implementation, always request the prototype handoff for the relevant screen from the user.
- When making the request, clearly specify which screen's prototype is needed (e.g., "Please share the prototype for the claim management list and detail screens from Claude Design").
- Do not begin HTML template implementation until the prototype has been provided.
- However, backend API, service, and repository layer implementation may proceed without a prototype.

### Prototype Usage Guidelines
- Reproduce the prototype using Go's html/template + htmx. Aim for a close approximation rather than a pixel-perfect reproduction.
- Common layout elements included in the prototype (sidebar, top bar) should be extracted as a Go layout template during the first handoff and reused across subsequent screen implementations.
- If the prototype contains framework-specific code such as React or Vue, rewrite it using htmx patterns.
- Reproduce the prototype's styles using Tailwind CSS classes.
